## 1. Purpose

Build a production-shaped proof of concept showing that Red Hat Developer Hub
can hold durable, agent-readable context for the delivery lifecycle of an RHDH
plugin.

The POC must connect four existing records without treating any one of them as
the complete plugin lifecycle:

1. the source `Component` from `rhdh-plugins`;
2. the overlay workspace `Component` from `rhdh-plugin-export-overlays`;
3. the Extensions Catalog `Plugin` and `Package` entities;
4. the workflow runs, jobs, attempts, and published OCI artifact.

The lifecycle backend stores normalized events, current projections, subject
mappings, synchronization state, and a one-time bootstrap marker in PostgreSQL.
Human and agent reads come from RHDH and do not call GitHub or a registry.

The Global Header incident is the primary demonstration. A second synthetic
workspace proves that the implementation contains no Global Header-specific
logic.

## 2. Definition of done

The work is complete only when all of the following are true:

- source, overlay, Extension Plugin, and Package entities can be resolved in
  the running RHDH Catalog;
- an overlay workflow job can be mapped to exactly one overlay Component;
- the collector can deterministically create or locate a lifecycle change;
- repeated workflow attempts update that change without creating duplicates;
- normalized events and current projections survive an RHDH backend restart;
- current and historical context agree across REST, UI, Actions Registry, and
  MCP;
- the delivery view includes the current Extensions Catalog package baseline,
  open PR candidates, and both the latest and latest-successful mainline build;
- the Lifecycle tab is an NFS extension built with Backstage UI and appears on
  `rhdh-overlay-workspace` Components;
- the Global Header fixture reaches a blocked verification state and later a
  successful publication state;
- a second workspace uses the same code and contracts;
- locally built dynamic plugins pass RHDH Local acceptance before anything is
  published;
- after local acceptance, digest-pinned packages are deployed to the current
  `rhdh-agentic-instance` and pass live smoke tests.

## 3. Non-negotiable architecture decisions

### AD-1: There is one Catalog API with multiple ingestion paths

RHDH exposes source Components, overlay Components, Extension Plugins, and
Extension Packages through the Backstage Catalog API.

- GitHub entity providers ingest the source and overlay Components.
- The catalog-index/Extensions Catalog integration ingests the custom `Plugin`
  and `Package` kinds.
- `/catalog` and `/extensions` are different user experiences and use different
  entity schemas, but the lifecycle backend resolves their entities through the
  Catalog service.

Do not ingest `workspaces/*/metadata/*.yaml` through the overlay GitHub entity
provider. Those files are inputs to the catalog-index pipeline.

### AD-2: The overlay Component is the lifecycle subject

For this POC, a lifecycle change is created for a Software Catalog Component
whose `spec.type` is `rhdh-overlay-workspace`.

Other entities are associations:

- source Component: where the plugin source lives;
- Extension Plugin: the product-level Extensions Catalog entry;
- Extension Package: a buildable/publishable package and its artifact metadata.

Users and agents may query lifecycle context by any associated entity ref, but
only an overlay workspace Component may be the subject of a newly created POC
change.

### AD-3: Relationships are derived, not trusted from action callers

`create-change` accepts a subject entity ref. It does not accept arbitrary
related entity refs.

The backend resolves associations from validated Catalog relations and
generated `rhdh.io/*` annotations on the overlay Component. This prevents a
caller from associating unrelated entities.

### AD-4: `changeId` remains the internal lifecycle identity

`changeId` is a UUID generated by the lifecycle backend. Pull requests, source
commits, workflow runs, jobs, artifacts, and agent attempts are evidence for a
change; they are not its primary database key.

External collectors additionally use a deterministic `externalChangeKey` so a
bootstrap retry or explicit refresh can find the same change.

### AD-5: Events are append-only and projections are reproducible

There is no public update or delete event API. After each event insertion, the
backend reads all events for the change ordered by `occurred_at` and database
ID, reduces them, and updates the current projection in the same transaction.

Historical reads replay the complete applicable history through
`occurredAt <= asOf`. `eventLimit` limits returned evidence, not the events used
to calculate the projection.

### AD-6: Ingestion may call source systems; reads may not

One bounded bootstrap and explicit subject refresh may call GitHub and may read current Catalog entities.
REST, Actions, MCP, and UI context reads use only the lifecycle database and the
RHDH Catalog service.

### AD-7: The standard GitHub Actions tab is supplementary

Keep the community GitHub Actions frontend plugin enabled. It shows repo-wide
workflow runs using the signed-in user's frontend credentials. It is not the
per-workspace lifecycle store and is not reused as a backend client.

### AD-8: The collector is an internal system writer

Public actions require authenticated human credentials and RBAC. The bootstrap/
refresh collector uses an internal domain service with an actor such as
`system:plugin-lifecycle/github-actions`.

Do not weaken the public human-identity guard to make the collector work. Do
not make the collector invoke the public HTTP action.

### AD-9: POC publication evidence and optional attestation

A successful GitHub job means that the matching workspace job succeeded. In the
delivery view, the Extensions Catalog Package is the released baseline and a
PR artifact is a candidate image. Neither is presented as proof of deployment
to a customer instance; each evidence source is labelled explicitly.

This is intentionally current-state evidence, not a cryptographic assertion
that this exact workflow run produced the artifact. The UI and API must label
it as Catalog-reported package evidence. A future attested mode may require a
workflow-produced `plugin-lifecycle-manifest.json`; that mode is optional and
must not block this POC.

### AD-10: Additive migration preserves existing history

Keep the existing change/event migration intact and add subject, binding, sync,
and bootstrap tables in an additive migration.

### AD-11: Use current Backstage construction patterns

Keep the repository structure produced by Backstage CLI. The frontend and its
development application use the New Frontend System, Backstage UI,
`createDevApp`, and `EntityContentBlueprint`. The frontend package also exports
a legacy `createPlugin` API surface and `Legacy` Scalprum module so the same
entity content can run on older RHDH deployments.

### AD-12: Local validation gates publication

Build and load the plugins from local package directories in RHDH Local first.
Publish OCI images and change the running agentic instance only after every
local gate is green.

## 5. Catalog metadata contract

### 5.1 Root overlay Component

Create `catalog-info.yaml` at the overlay repository root:

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: rhdh-plugin-export-overlays
  title: RHDH Plugin Export Overlays
  description: Packaging and OCI publication layer for RHDH dynamic plugins.
  annotations:
    github.com/project-slug: rhdh-parasol/rhdh-plugin-export-overlays
spec:
  type: repository
  lifecycle: experimental
  owner: rhdh-team
  system: rhdh
```

### 5.2 Overlay workspace Component

Generate `workspaces/<workspace>/catalog-info.yaml` for every eligible
workspace containing both `source.json` and `plugins-list.yaml`.

Required shape:

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: overlay-<workspace>
  title: Overlay workspace <workspace>
  annotations:
    github.com/project-slug: rhdh-parasol/rhdh-plugin-export-overlays
    rhdh.io/overlay-workspace: <workspace>
    rhdh.io/source-repository: <owner/repository>
    rhdh.io/source-revision: <source.json repo-ref>
    rhdh.io/source-entity-ref: <canonical ref when verified>
    rhdh.io/extensions-plugin-refs: <sorted comma-separated canonical refs>
    rhdh.io/extensions-package-refs: <sorted comma-separated canonical refs>
  links:
    - title: Overlay workspace
      url: https://github.com/rhdh-parasol/rhdh-plugin-export-overlays/tree/main/workspaces/<workspace>
    - title: Source repository
      url: <source URL from source.json>
    - title: Export workflows
      url: https://github.com/rhdh-parasol/rhdh-plugin-export-overlays/actions
spec:
  type: rhdh-overlay-workspace
  lifecycle: experimental
  owner: rhdh-team
  system: rhdh
  subcomponentOf: component:default/rhdh-plugin-export-overlays
  dependsOn:
    - <verified source Component ref, when one exists>
```

Annotation rules:

- omit an optional annotation instead of writing an empty value;
- use canonical lower-case entity refs;
- store multiple refs as comma-separated values with no spaces;
- sort refs so generation is deterministic;
- package refs come from `workspaces/<workspace>/metadata/*.yaml`;
- Plugin refs come from Extension Plugin YAML whose `spec.packages` names one
  of the workspace Package entities;
- never derive Component names from naming conventions when a source
  `catalog-info.yaml` can be inspected;
- unresolved source Components are allowed and reported;
- ambiguous Package-to-Plugin or source mappings fail generation.

### 5.3 Generator behavior

Add `scripts/generate-catalog-info.py` with `--check` support.

The generator must:

1. enumerate only `workspaces/*`, never `workspaces/**`;
2. ignore e2e fixtures and scaffolder skeletons;
3. parse and validate `source.json`, `plugins-list.yaml`, Package YAML, and
   Extension Plugin YAML;
4. inspect a source workspace's actual `catalog-info.yaml` at the pinned source
   ref when resolving the source Component;
5. allow a small checked-in overrides file only for exceptional mappings;
6. write a deterministic mapping report listing resolved, unresolved, and
   ambiguous workspaces;
7. exit non-zero for malformed inputs, ambiguity, or generated-file drift;
8. allow an unresolved optional source Component without guessing a ref.

Add generator tests using temporary fixture trees. Do not modify real workspace
fixtures during tests.

## 6. Lifecycle storage model

Replace the initial migration with the following logical schema.

### `lifecycle_changes`

- `id`: UUID primary key;
- `request_id`: unique idempotency key;
- `request_payload_json`: canonical compact create input;
- `subject_entity_ref`: overlay Component ref;
- `origin`: `action`, `github-actions`, or `fixture`;
- `external_change_key`: nullable unique collector correlation key;
- `title`, `summary`;
- `current_phase`, `current_state`;
- `projection_json`;
- `created_by`, `created_at`, `updated_at`, `projected_at`.

Indexes:

- `(subject_entity_ref, updated_at)`;
- unique `request_id`;
- unique nullable `external_change_key`.

### `lifecycle_change_entities`

- `change_id`: foreign key to `lifecycle_changes`;
- `entity_ref`;
- `role`: `subject`, `source`, `overlay`, `extension-plugin`, or `package`;
- `relation_source`: `catalog-relation`, `catalog-annotation`, or `subject`;
- `created_at`.

Primary key: `(change_id, entity_ref, role)`.

Indexes: `entity_ref` and `change_id`.

### `lifecycle_events`

Retain the current append-only structure:

- ordered numeric database ID;
- unique `event_id`;
- `change_id`;
- schema version and event kind;
- occurred/ingested timestamps;
- actor, producer, and compact payload JSON.

### `lifecycle_ingestion_diagnostics`

- `diagnostic_id`: deterministic unique ID;
- `source`;
- optional `subject_entity_ref`;
- `external_id`;
- `reason_code`;
- human-readable `summary`;
- compact `details_json`;
- `first_seen_at`, `last_seen_at`, optional `resolved_at`.

Allowed reason codes for the first implementation:

- `workspace_not_found`;
- `workspace_ambiguous`;
- `source_descriptor_missing`;
- `source_ref_invalid`;
- `change_correlation_failed`;
- `change_correlation_ambiguous`;
- `package_entity_missing`;
- `artifact_digest_pending`;
- `github_api_error`.

Do not store complete GitHub responses or logs in diagnostics.

### 7.2 Create change

Action ID: `plugin-lifecycle:create-change`

```ts
type CreateChangeInput = {
  requestId: string;
  subjectEntityRef: string;
  title: string;
  summary?: string;
  target?: {
    rhdhVersion?: string;
    backstageVersion?: string;
    pluginVersion?: string;
  };
  initialReferences?: LifecycleReference[];
};
```

Behavior:

- canonicalize the subject ref;
- require an existing Catalog `Component` with
  `spec.type: rhdh-overlay-workspace`;
- resolve and persist all verified associations;
- create the system-owned `change.created` event;
- return the existing change for identical `requestId` input;
- return conflict for a reused `requestId` with different input.

### 7.3 Record event

Action ID: `plugin-lifecycle:record-event`

Keep `eventId`, `changeId`, `occurredAt`, `producer`, and the typed event
payload. `change.created` is not externally recordable.

Identical reuse of `eventId` returns the stored result. Different reuse returns
conflict.

### 7.4 Get context

Action ID: `plugin-lifecycle:get-context`

```ts
type GetContextInput = {
  entityRef: string;
  changeId?: string;
  asOf?: string;
  eventLimit?: number; // default 100, maximum 500
};
```

REST equivalent:

```text
GET /api/plugin-lifecycle/context
  ?entityRef=<canonical-or-parseable-ref>
  &changeId=<optional-uuid>
  &asOf=<optional-ISO-8601>
  &eventLimit=<optional-1-to-500>
```

For clients that address an Extension Plugin directly, the backend also
accepts the compatibility form
`GET /api/plugin-lifecycle/plugins/:namespace/:name/context` and resolves it
as `plugin:<namespace>/<name>`. The NFS UI uses the generic entity-reference
form so it can render the overlay Component subject and all of its
associations.

Response:

```ts
type LifecycleContext = {
  schemaVersion: number;
  requestedEntityRef: string;
  subject: CatalogEntitySummary;
  relatedEntities: CatalogEntitySummary[];
  warnings: Array<{ code: string; message: string; entityRef?: string }>;
  changes: LifecycleChangeSummary[];
  selectedChange?: LifecycleChangeSummary;
  projection?: LifecycleProjection;
  events: LifecycleEvent[];
  asOf?: string;
};
```

Selection rules:

- query changes where the requested ref is either the subject or an
  association;
- if `changeId` is supplied, require it to be associated with the requested
  ref;
- otherwise select the most recently updated change whose state is not
  `succeeded` or `superseded`;
- fall back to the most recently updated change;
- treat `failed` as retryable/non-terminal because another build attempt may
  continue the same change;
- return stored history when a Catalog entity was deleted and mark that entity
  `missing`;
- return no projection when `asOf` predates `change.created`.

## 9. Association resolution

Implement one `EntityAssociationResolver` used by public creation and the
collector.

Given an overlay Component, it must:

1. add the Component itself as both `subject` and `overlay`;
2. read `spec.dependsOn` and `rhdh.io/source-entity-ref` for the source role;
3. parse `rhdh.io/extensions-plugin-refs`;
4. parse `rhdh.io/extensions-package-refs`;
5. canonicalize and deduplicate all refs;
6. fetch the entities from the Catalog using the caller's credentials for a
   public action, or the lifecycle plugin's service credentials for the
   collector;
7. persist missing optional refs as associations so historical context still
   identifies them;
8. return warnings for missing entities;
9. reject malformed or contradictory subject metadata.

Do not infer relationships by comparing display names at runtime.

## 10. GitHub Actions collector

### 10.1 Configuration

Add this backend configuration shape:

```yaml
pluginLifecycle:
  githubActions:
    enabled: false
    repository: rhdh-parasol/rhdh-plugin-export-overlays
    workflow: publish-workspace-plugins.yaml
    requireManifest: false
```

The example app defaults collection to false. RHDH Local and the deployed
instance enable it explicitly after configuring the GitHub App integration.
Package `dynamicArtifact` values are displayed as the released Extensions
Catalog baseline. PR candidate images come from the existing
`published-exports-pr-<number>` artifact. `requireManifest: true` is retained
only as an optional future attested mode. There is no recurring collector
schedule in this POC.

### 10.2 Authentication

Use backend integrations and the GitHub credentials provider:

- `ScmIntegrations.fromConfig`;
- `DefaultGithubCredentialsProvider.fromIntegrations`;
- Octokit created with the returned GitHub App token.

Required GitHub App repository permissions:

- Actions: Read;
- Contents: Read;
- Pull requests: Read when PR correlation is enabled;
- Metadata: Read.

Fail startup only for invalid configuration. An API outage records a compact
diagnostic and leaves the cached context available for a later explicit
refresh.

### 10.3 Bootstrap and refresh algorithm

During the one-time bootstrap, and for a later explicit subject refresh:

1. resolve exactly one Catalog Component with
   `rhdh.io/overlay-workspace=<workspace>` and the matching project slug;
2. list open PRs and a bounded recent window of closed PRs;
3. match exact workspace files and read commit statuses with bounded
   concurrency;
4. derive each external change key, then create or retrieve lifecycle changes
   idempotently;
5. append PR, source, status, and phase events using deterministic event IDs;
6. for PRs with a successful publish check, read the exact
   `published-exports-pr-<number>` artifact when it is still retained;
7. collect the latest workflow runs and exact workspace jobs for main/release
   runs using bounded concurrency;
8. mark prior diagnostics resolved when the same external record becomes
   processable.

Bootstrap fetches each repository/workflow run list once and processes a bounded
queue. PR discovery fetches open PRs plus the most recently updated closed PRs,
limited by `pluginLifecycle.githubActions.closedPullRequestsPerWorkspace` (3
per workspace by default, with a repository-wide scan cap of 100). Closed and
merged changes remain available for history but are not active candidates.
After bootstrap, GitHub is contacted only by an explicit refresh (or the agent
action's `refreshPolicy: if_stale` path).

### 10.4 Change correlation

For a pull-request run:

```text
externalChangeKey =
  github:<repository>:pr:<number>:workspace:<workspace>
```

For a non-PR run:

use the observed branch and commit directly:

```text
externalChangeKey =
  github:<repository>:ref:<branch>:commit:<head-sha>:workspace:<workspace>
```

Derive `requestId` as `github-actions:` plus the SHA-256 hash of the external
change key so it remains below the database length limit.

If a workspace, PR, source record, or Component cannot be resolved exactly,
write a diagnostic and do not create a guessed change.

### 10.5 Deterministic event IDs

Use the following logical inputs:

```text
CI snapshot:
github-actions:<repository>:<runId>:<runAttempt>:<jobId>:<status>:<conclusion-or-none>:<github-updated-at>

Generated phase update:
<ci-snapshot-event-id>:phase

Artifact:
catalog-package:<package-ref>:<digest>
```

Hash the complete logical value when necessary to stay within 200 characters.

### 10.6 Phase mapping

The collector appends an explicit `phase.updated` event after each CI snapshot:

| GitHub job                                                  | Phase | State     |
| ----------------------------------------------------------- | ----- | --------- |
| queued                                                      | build | pending   |
| in progress                                                 | build | running   |
| completed / success                                         | build | succeeded |
| completed / failure or timed out                            | build | failed    |
| completed / cancelled, skipped, neutral, or action required | build | blocked   |

The fixture may add explicit implementation and verification phase events that
cannot be inferred safely from generic workflow job metadata.

### 10.7 Artifact resolution

For an open or recently closed PR, read the exact
`published-exports-pr-<number>` artifact after a successful `publish` check.
Validate its archive, metadata, workspace, PR revision, and image references,
then emit compact candidate-image artifact events. Expired or missing artifacts
are reported as unavailable; image names are never guessed. The Extensions
Catalog Package `dynamicArtifact` remains a separate released-baseline fact and
is never written into a PR change as run evidence. The POC does not call a
registry directly.

## 11. Projection rules

- `change.created` starts at `intent/pending`.
- Only `phase.updated` changes phase/state, except `change.superseded`, which
  sets `superseded`.
- CI, verification, artifact, reference, and agent events update their evidence
  collections without silently changing phase/state.
- A repeated CI identity replaces the current projection entry but not event
  history.
- A repeated reference identity replaces that reference in the projection.
- Artifact identity is package ref plus digest.
- `winningRun` is set only after immutable artifact resolution succeeds.
- Late events trigger full deterministic reprojection.
- Phase movement is not monotonic; verification may return a change to
  implementation.

Replace the local SQLite adaptation with a PostgreSQL service in the generated
Compose override:

- use a pinned PostgreSQL image;
- use `.env` values for database, user, and password;
- add a named volume;
- add a health check;
- make RHDH depend on the healthy database;
- generate the local `backend.database.connection` configuration;
- retain the volume across an ordinary `local-down`/restart.

The restart acceptance test is an RHDH container restart, not a volume deletion.

### 14.3 Local synchronization

The local demo uses the same one-time bootstrap and explicit subject refresh as
the deployed configuration. UI polling, when bootstrap is running, reads only
the persisted RHDH context and never calls GitHub directly.
